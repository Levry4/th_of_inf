|---|---|

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| Silo | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Используется в текущем Docker Compose-примере Lakekeeper как альтернатива MinIO. Даёт S3 API и позволяет хранить Parquet-файлы Iceberg в объектном хранилище. |
| PostgreSQL 17 | БД, где Lakekeeper хранит метаданные каталога | Надёжная реляционная СУБД с открытым исходным кодом, подходящая для хранения служебных метаданных каталога. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Даёт единый каталог таблиц Iceberg и позволяет подключать разные движки (Trino, Spark) к общим метаданным. |
| Trino 476 | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в объектное хранилище | Поддерживает SQL, Iceberg и работу с объектным хранилищем. Использовался для создания слоёв и выполнения аналитического запроса. |
| Jupyter + Spark | Второй движок для работы с lakehouse | Spark подключается к Lakekeeper через Iceberg REST Catalog и читает данные независимо от Trino, позволяет демонстрировать Schema Evolution и Time Travel. |
| StarRocks | Дополнительный сервис из Compose | Описан в конфигурации, но в момент проверки контейнеров не был запущен; в выполнении Q16 не участвовал. |

> **Примечание:** в текущем стенде используется Silo, а не MinIO — это альтернативное S3-совместимое хранилище. В отчёте указан фактически использованный сервис.

### Скрипты, которыми поднимал стек

Основной файл развертывания — `docker-compose.yaml` из каталога `examples/minimal` официального репозитория Lakekeeper.

```bash
# Перейти в каталог примера
cd /tmp/lakekeeper-example/examples/minimal

# Запустить сервисы из Docker Compose (Silo, PostgreSQL, Lakekeeper, Trino и т.д.)
docker compose up -d

# Проверить работающие контейнеры
docker ps

# Посмотреть сервисы, описанные в Compose
docker compose config --services

# Подключиться к Trino (SQL-движок)
docker compose exec trino trino

# Отдельно поднять Jupyter (Spark — второй движок)
docker compose up -d --no-deps jupyter
```

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `part` | `partkey`, `brand`, `type`, `size` | Джойн по `partkey`; фильтр по `brand <> 'Brand#45'`, `type NOT LIKE 'MEDIUM POLISHED%'`, `size IN (...)`; группировка и вывод. |
| `partsupp` | `partkey`, `suppkey` | Джойн с `part` по `partkey`; подсчёт `COUNT(DISTINCT suppkey)`. |
| `supplier` | `suppkey`, `comment` | Подзапрос: исключение поставщиков, в `comment` которых встречается `%Customer%Complaints%`. |

Исходный запрос Q16:

```sql
SELECT
    p.brand,
    p.type,
    p.size,
    count(DISTINCT ps.suppkey) AS supplier_cnt
FROM tpch.sf1.partsupp AS ps
JOIN tpch.sf1.part AS p ON p.partkey = ps.partkey
WHERE p.brand <> 'Brand#45'
  AND p.type NOT LIKE 'MEDIUM POLISHED%'
  AND p.size IN (49, 14, 23, 45, 19, 3, 36, 9)
  AND ps.suppkey NOT IN (
      SELECT suppkey
      FROM tpch.sf1.supplier
      WHERE comment LIKE '%Customer%Complaints%'
  )
GROUP BY p.brand, p.type, p.size
ORDER BY supplier_cnt DESC, p.brand, p.type, p.size;
```

## 5. Тесты производительности

Для сравнения сжатия созданы две тестовые таблицы с одинаковыми 200 000 строк из Bronze.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | не замерено отдельно | 4,394 (тестовая таблица, 200 000 строк) | ZSTD дал размер примерно на 1,87% меньше GZIP (82 126 байт). По размеру выигрывает ZSTD; по времени Q16 вывод сделать нельзя — замеры для обоих кодеков не проводились. |
| ZSTD | не замерено отдельно | 4,312 (тестовая таблица, 200 000 строк) | ZSTD компактнее на ~1,87%. Для окончательного вывода о скорости нужно отдельно замерить Q16 на GZIP и ZSTD. |

Замер запроса Q16 на Bronze:

| Запрос | Общее время команды |
|---|---:|
| Q16 на Bronze | 8,642 секунды |

Время получено командой `time docker compose exec trino trino --execute ...`; оно включает запуск Docker-команды и Trino CLI, поэтому не является чистым временем выполнения SQL.

**Ограничение эксперимента:** время Q16 отдельно для GZIP и ZSTD ещё не измерено; указанные размеры получены на тестовых таблицах, а не на всей Bronze. По имеющимся данным можно сравнить размер файлов, но нельзя достоверно утверждать, какой кодек быстрее выполняет Q16.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse объединяет хранение в объектном хранилище с управлением таблицами и аналитической обработкой. Объектное хранилище удобно для больших объёмов файлов, а Iceberg даёт управление метаданными, снимками и изменениями схемы. Благодаря этому разные движки (Trino и Spark) могут работать с общими таблицами. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В демонстрационной таблице Iceberg добавлена новая колонка: `ALTER TABLE lakekeeper.gold.iceberg_features_demo ADD COLUMN schema_demo STRING;`. Схема обновилась, существующие данные не пришлось пересоздавать; новая колонка заполняется для последующих записей. |
| Пример скрипта восстановления данных из снапшота (time travel) | Сохранён id старого снимка `857657110169374553`. После вставки тестовой строки таблица содержала 101 запись, а запрос к старому снимку вернул 100: `SELECT count(*) FROM lakekeeper.gold.iceberg_features_demo VERSION AS OF 857657110169374553;`. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark в Jupyter | Позволяет читать таблицы Iceberg независимо от Trino, выполнять преобразования и демонстрировать работу с историей снимков и изменением схемы. |

Spark подключён к Lakekeeper через Iceberg REST Catalog с использованием S3-совместимого хранилища. В ноутбуке выполнено чтение `lakekeeper.bronze.part` — вернулось 200 000 строк; также прочитана витрина `lakekeeper.gold.q16_result`.

Адрес каталога внутри Docker-сети:

```text
http://lakekeeper:8181/catalog
```

Скрипт запуска Jupyter:

```bash
docker compose up -d --no-deps jupyter
```

Ноутбук `notebooks/Spark.ipynb` нужно включить в репозиторий для проверки действий.

## 7. Выводы

В ходе работы реализован аналитический запрос TPC-H Q16 на архитектуре Bronze/Silver/Gold с использованием Apache Iceberg. Bronze сохраняет исходные данные, Silver подготавливает их для анализа, Gold содержит компактный агрегированный результат. Trino выполняет SQL-обработку, Lakekeeper управляет каталогом Iceberg, а Spark позволяет независимо читать те же таблицы и демонстрировать Schema Evolution и Time Travel. В тесте на одинаковом объёме данных ZSTD дал размер файлов примерно на 1,87% меньше GZIP; для окончательного вывода о производительности нужно отдельно замерить время Q16 для обоих кодеков.
